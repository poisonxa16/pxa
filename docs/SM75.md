# SM75 source build and tuning

This source configuration targets Turing cards such as the RTX 2080 Ti, Titan RTX and Tesla T4. Select the architecture explicitly:

```sh
cmake -S . -B build-sm75 \
  -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=75 \
  -DPXA_PXQN_CLOSED_SRC=OFF -DPXA_PXQ_ENCODER=OFF
cmake --build build-sm75 --target llama-bench llama-server test-backend-ops -j 12
```

Use `-DCMAKE_CUDA_ARCHITECTURES="70;75"` for a V100 and Turing build. Hardware support in a local source build does not change the architecture list of a downloaded release.

## Dense standard-quant matrix multiplication

`PXA_TURING_CUBLAS_NE11` selects the batch width at which dense Q4_0, Q8_0, Q4_K, Q5_K and Q6_K matrix multiplication changes from INT8 MMQ to dequantization followed by FP16 cuBLAS. The ENHANCE default is `256`; DEFAULT and REFERENCE retain `64`. Models whose profile contains PXQ2, PXQ3, PXQ4 or PXQ4HQ tensors also retain `64`: the higher crossover regressed PXQ4 prefill in an end-to-end measurement. A value of `0` keeps MMQ. An explicit value overrides the model default. The threshold is resolved again when the model profile changes; the startup banner prints the initial value and the `PXA_AUTO` model-profile line prints the model's value. It applies only to SM75; other quant types, the existing routed-expert selector and the dedicated PXQ/PXQN kernels keep their policies. Compile-time `GGML_CUDA_FORCE_MMQ` and `GGML_CUDA_FORCE_CUBLAS` still take precedence.

For an A/B comparison, run the same model, batch size and cache settings with `PXA_TURING_CUBLAS_NE11=64` (the previous policy) and `PXA_TURING_CUBLAS_NE11=256`. Changing the route changes floating-point arithmetic, so compare numerical correctness and generated output as well as speed.

The backend suite has an opt-in set of 60 CPU-reference comparisons covering Q4_0, Q8_0, Q4_K, Q5_K and Q6_K, including widths immediately around both crossover points:

```sh
PXA_BO_TURING_MATMUL=1 PXA_TURING_CUBLAS_NE11=64 build-sm75/bin/test-backend-ops test -o MUL_MAT -b CUDA0
PXA_BO_TURING_MATMUL=1 PXA_TURING_CUBLAS_NE11=256 build-sm75/bin/test-backend-ops test -o MUL_MAT -b CUDA0
PXA_BO_TURING_MATMUL=1 PXA_TURING_CUBLAS_NE11=0 build-sm75/bin/test-backend-ops test -o MUL_MAT -b CUDA0
```

Use a GPU UUID in `CUDA_VISIBLE_DEVICES` when selecting a card: the CUDA device ordinal can differ from the index printed by `nvidia-smi`.

## PXQN library

The public source does not contain the PXQN kernel implementations. Use an authorized, compatible `libggml-pxqn.so` through `PXA_PXQN_LIB` as described in [the source build guide](../BUILD-FROM-SOURCE.md#4b-pxqn-files-with-a-source-build). Check the actual library's architecture coverage with `cuobjdump --list-elf`; a package name or README support table alone does not establish which cubins it contains.

These changes preserve the existing selector symbol, backend context, tensor and topology struct layouts. This reduces compatibility risk but does not replace a runtime check with the matching library. Kernel presence, successful library loading and successful PXQN inference are separate checks. The encoder is unnecessary for benchmarking existing models.

## Flash-Next batch cells

Two narrowly scoped cells cover the tested Flash-Next PXQN 32GB file layout: one SM75 card in the 22 GB class, and that card paired with a 32 GB V100 in either device order. They start from `-b 2048 -ub 2048`. The pair retains the existing layer-split and automatic placement policies; no expert counts, cold-path policy or learning settings are changed.

The match checks architecture, layer/expert/KV-head counts, encoded tensor count, total file size and PXQN encoder metadata. Ordinary 11 GB 2080 Ti cards, T4 cards, 24 GB Turing cards, other model layouts and other mixed topologies retain their previous choices. This is a file-layout match, not a cryptographic identification of model weights.

The cells are labelled `FIT`: the context must allocate and leave the configured runtime VRAM reserve. If necessary the engine walks down its existing microbatch ladder. The launcher sends VRAM capacity with SM75 topology hints and leaves these batch flags to the engine, so a UI launch does not turn a candidate into an unchecked explicit override. User-provided `-b` and `-ub` still win, and DEFAULT/REFERENCE retain their policies. In a clean source-runtime server check at context 4096/F16 K/V, 2048 left 429 MiB free; the engine stepped down to 1024 with 923 MiB free, exceeding its 512 MiB reserve, and served a generation request successfully.

The initial measurements used the installed v4 runtime, its UI-exported Flash-Next kernel preset, F16 K/V, batch 2048, eight threads, no speculation and frozen expert learning. At an 8192-token prompt, microbatch 1024 versus 2048 gave 856.30 versus 898.33 t/s on the 22 GB RTX, and 1195.54 versus 1273.62 t/s on the pair. The pair kept the UI-derived RTX/V100 weight ratio 407/593. These are controlled prefill measurements, not a full UI/MTP or long-context quality qualification, and do not establish that two GPUs are faster than one V100 for every workload. Source builds must use their matching decoder library.

## Further work

The `mistrjirka/llama.cpp` `v100-optimized` branch has Turing D256 long-context Q8 attention and native Q8 K reads for small verifier batches. PXA uses an older attention implementation, so those changes require a kernel port with their layout and Stream-K correctness fixes, rather than applying the final small commits alone. The routed MoE MMQ implementation also differs. Neither port is enabled by the dense crossover change.
